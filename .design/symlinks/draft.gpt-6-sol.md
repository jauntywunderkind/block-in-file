# Symlink policy for block-in-file file targets

## Situation and decision

Compfuzor manages configuration via symlinks into system directories. A BIF update to one of these paths can silently turn the link into a regular file, while a consumer writing through the same path edits the referent. This proposal addresses **the final component of a file operand**, not symlinked parent directories. It feeds the existing `bif-symlinks` issue; it does not update the ticket.

**Recommend `--symlink=follow` by default**, with explicit `replace` and `error` alternatives. The default should preserve the path topology and reconcile the same file that reads observe. `replace` retains today's atomic rename-over behavior for callers deliberately deploying a regular file over a symlink; changing the default is a documented compatibility break for those callers. `error` is appropriate for users who want an explicit choice on every link. There is no evidence in this source of a caller intentionally relying on implicit de-linking; an explicit opt-in keeps that capability without making it an accidental outcome.

## Current implementation: evidence and limits

- The CLI's `--read` branch passes the operand to `io.readFile` and never calls `processFile` ([`block-in-file.ts:65-103`](/block-in-file.ts#L65-L103)). Normal processing checks existence with `io.fileExists` and reads the same operand ([`block-in-file.ts:126-143`](/block-in-file.ts#L126-L143)). The IO plugin implements these via `fs.access` and `fs.readFile`, which follow symlinks ([`src/plugins/io.ts:36-59`](/src/plugins/io.ts#L36-L59)). Thus a valid symlink to a file is read as its referent. `--read` has no symlink-specific logic.
- Insertion writes `${file}.prevalidate` or `${file}.atomic`, then `io.rename(tempFile, file)` ([`src/file-processor.ts:357-380`](/src/file-processor.ts#L357-L380)); removals have a separate but identical path ([`src/file-processor.ts:249-285`](/src/file-processor.ts#L249-L285)). IO's rename is `fs.rename` ([`src/plugins/io.ts:64-65`](/src/plugins/io.ts#L64-L65)). Renaming onto a final-component symlink replaces that directory entry, **not** its referent. The `.atomic` suffix is predictable, not a unique secure tempfile. The validator sees the *candidate temp path*, not the symlink path ([`src/file-processor.ts:360-369`](/src/file-processor.ts#L360-L369), [`src/validation.ts:4-10`](/src/validation.ts#L4-L10)). The old ticket's description of a direct write-through and validation of the symlink path is out of date for these branches.
- `--mode=ensure` or `only` can return before the rename, but the default `none` does not ([`src/plugins/config.ts:284-288`](/src/plugins/config.ts#L284-L288), [`src/file-processor.ts:300-318`](/src/file-processor.ts#L300-L318)). Removal does not apply this skip gate, and even an absent matching block reaches its rename branch ([`src/file-processor.ts:213-297`](/src/file-processor.ts#L213-L297)). Therefore destruction is conditional on reaching a write, not inevitable for *every* invocation.
- Backup runs before the rename only when `output === "---"`; removal and insertion both pass the original operand and the already-read content ([`src/file-processor.ts:249-257`](/src/file-processor.ts#L249-L257), [`src/file-processor.ts:346-355`](/src/file-processor.ts#L346-L355)). `performBackup` derives its name from that path (or its basename in `--backup-dir`), checks accessibility, then uses `fs.copyFile` ([`src/backup.ts:53-61`](/src/backup.ts#L53-L61), [`src/backup.ts:79-80`](/src/backup.ts#L79-L80), [`src/backup.ts:127-165`](/src/backup.ts#L127-L165)). A symlink therefore currently yields a *regular-file copy of referent content* named after the link, not a snapshot of the link. By default backup errors are swallowed unless `--state-on-fail=fail` ([`src/backup.ts:159-165`](/src/backup.ts#L159-L165)).
- `--attributes` is `chattr` applied **after** the rename to `file`, with warnings rather than fatal errors for many failures ([`src/file-processor.ts:376-380`](/src/file-processor.ts#L376-L380), [`src/attributes.ts:118-160`](/src/attributes.ts#L118-L160)). It is not ownership, mode, xattr, or SELinux preservation. The rename creates/replaces an inode, with consequences for ownership, permission bits, existing xattrs and hardlink peers regardless of whether the renamed-over entry was the symlink or its referent. See open `bif-ecy` (owner/group) and `bif-ccn` (SELinux); neither is solved here.
- There are two exceptional writes: when creating a missing file or `before === true`, `processFile` first calls `io.writeFile(file, "")` (which follows symlinks) before the atomic path ([`src/file-processor.ts:320-324`](/src/file-processor.ts#L320-L324), [`src/plugins/io.ts:42-50`](/src/plugins/io.ts#L42-L50)). `--output=PATH` writes directly via IO rather than rename and follows an existing output link ([`src/file-processor.ts:382-385`](/src/file-processor.ts#L382-L385)); `--output=--` actually still takes the rename branch, despite the IO plugin treating `--` as no-op ([`src/file-processor.ts:357-376`](/src/file-processor.ts#L357-L376), [`src/plugins/io.ts:47-49`](/src/plugins/io.ts#L47-L49)). These are existing behavioral inconsistencies, not evidence that the main update follows links.
- For a symlink in a *parent* directory, the filesystem resolves that directory when accessing both `${file}.atomic` and `file`; the final file component is not a link, so the rename updates the file inside the linked directory and leaves the parent link intact. This differs from a symlink at the final component, which rename overwrites.

The mixed-writer split-brain described by compfuzor follows directly from this sequence: the consumer's ordinary write follows the link, while BIF reads the referent and then renames over the link. After BIF runs, the referent retains the earlier consumer content and the newly created file at the link name contains BIF's update. BIF source explains the mechanism; the particular apt incident is consumer evidence, not a claim that this repo has an integration test for compfuzor.

## Contract

Expose `--symlink=follow|replace|error`; reject other values rather than silently treating them as the default. Detect **only the final path component** using `lstat` (not `stat` or `access`), so symlinked parents remain traversable. For `ENOENT` distinguish no final entry from a dangling link with `lstat` before treating a path as creatable; propagate other filesystem errors. Detect and decide before any mutation, including the preparatory direct writes, backup, validation temp creation, and attribute application. Use the same decision for removal-only invocations.

| Policy | On a final-component symlink | `--read` | Backup / attributes |
| --- | --- | --- | --- |
| `follow` (default) | Resolve the chain with `realpath` and update the resolved regular file; preserve every link in the chain. A dangling or cyclic link fails explicitly; never materialize or replace it as a new file. | Read the referent (as today). | Backup the referent's old bytes; apply `--attributes` to its new inode. |
| `replace` | Deliberately rename over the final link, leaving the old referent untouched; warn on this topology change or make the flag's meaning unmistakable in help. | Read referent content to match the existing operation's input; this mode describes the write destination, not a request to read link text. | Backup the old referent bytes as today, **not** the link object; apply attributes to the new regular file at the operand. Document that backup cannot reconstruct the lost link pointer. |
| `error` | Refuse before any write or backup: `Path is a symlink: <path>; use --symlink=follow or --symlink=replace` (include the path). | Also refuse, for a consistent policy; `--read` must not consume stdin or mutate anything. | No backup and no attributes. |

`--read` on regular files and symlinked parent directories remains unchanged for all modes. A dangling final symlink under `replace` should still require an explicit choice: resolve no content, then follow existing missing-file/create semantics only if those are valid for the operation; do not silently turn read failure into empty existing content. For a missing **non-symlink** final component, retain creation behavior; no `realpath(file)` is available until it exists. Read-only previews to stdout should not mutate anything; a decision on whether an explicit output path is a symlink must be made against the **actual output destination**, not just the input operand.

### Follow mechanics and write boundary

Resolve a linked file to `effectiveFile = await realpath(file)` **before all file writes**. Keep `file` as the user-facing operand for messages, diff headers, and source attribution; pass `effectiveFile` consistently to the existence/read, preparatory write, backup, validation-temp, rename, and post-write attribute operations. Both insertion and removal should use a shared destination/write helper rather than reproducing the path substitution in two branches. Example: `/etc/apt/sources.list.d/x.sources -> /opt/managed/x.sources` writes `/opt/managed/x.sources.atomic` and renames it to `/opt/managed/x.sources`; `/etc/apt/.../x.sources` remains a symlink. A relative link and a multi-hop chain receive the same treatment via `realpath`.

Preserve prevalidation: `${effectiveFile}.prevalidate` holds candidate content and is validated *before* rename. Validation receives this candidate path (not the original link or the installed target). The temp must be in the resolved file's directory to preserve same-filesystem rename atomicity at the actual destination, including when the link and referent lie on different mounts. Existing predictable temp suffixes and rollback/cleanup limitations are separate hardening work, not fixed by path resolution. Ensure `--mode` skip paths never touch the linked file; resolve early enough to reject forbidden symlinks but do not create temporary files on a skipped run.

Make backup naming explicit: under `follow`, pass the resolved path to `performBackup` so the default backup is **beside the referent**, e.g. `/opt/managed/x.sources.bak`; with `--backup-dir`, use the referent's basename in that directory. It copies the referent's old content, never the symlink object. Under `replace`, preserve current link-path naming and content-copy semantics. This changes backup placement relative to today's implicit replace behavior; callers relying on `${link}.bak` can opt into `replace` (or use `--backup-dir`). Retain `state-on-fail` behavior but make this path choice visible in docs. If named output (`--output=PATH`) is used, its direct-write path currently follows output symlinks and is non-atomic: route destination policy through that path too, or refuse final symlinks there until it can share the atomic writer; never claim `replace` works while direct `writeFile` still follows. `--output=--` currently writes despite its advertised no-output meaning and deserves a separate correction before claiming comprehensive non-writing guarantees.

`realpath` and `lstat` do not prevent a privileged actor from racing a link swap between detection and rename. Recheck immediately before committing where practical and fail on a changed link/target rather than knowingly redirecting a write. Neither this proposal nor the existing rename writer offers a security guarantee against hostile concurrent directory mutation; that requires a stronger descriptor-relative transaction design. Following a link also does **not** edit an existing inode in place: it atomically replaces the referent's inode. Hardlinks to that inode retain the prior content. Permission bits, ownership, xattrs and labels may differ after the rename; do not claim that symlink safety solves the separate inode-preservation problems.

## Test plan

Use Vitest integration tests with `fs/promises`, `mkdtemp`/`rm`, and CLI invocation like [`test/read-cli.test.ts:1-29`](/test/read-cli.test.ts#L1-L29); assert with `lstat`, `readlink`, `realpath`, `stat` and content from **both** link and target, not only `readFile(link)`.

1. Default and explicit `follow`: update a link to a file in another directory; link target string and link type survive, referent changes, no regular file at link, temp/backup located beside referent. Include relative and chained links and a referent on a different mount where feasible (or assert paths with an injected IO fake).
2. `replace`: link becomes a regular file with new content; old target is unchanged. `error`: link and referent remain byte-identical, diagnostic includes path and both explicit alternatives; test an invalid flag value.
3. Read a linked block with `--read` under each mode (follow/replace return old body, error refuses), with no writes or backups. Include a symlinked directory in the middle of the operand under all modes: it must work as an ordinary file.
4. `--backup` and `--backup-dir` for follow versus replace: inspect backup names and contents, link survival, and failure mode before mutation. Test prevalidation success and failure for follow, verifying candidate path is beside referent and failure leaves link and referent intact. `--attributes` can be checked via an IO/command mock or debug path without depending on privileges; ensure the chosen path is the actual destination.
5. Removal-only on a linked file in all three modes; input must not wait for stdin. Test removal of an existing block and no matching block. Confirm any rename still respects the policy. Include `--mode=ensure` skip (no temp or topology change) and preparatory `--create` / BOF branch.
6. Dangling and cyclic final links (follow/error refuse without replacement; explicit replace documented behavior), and missing non-link file creation. Assert both output forms: ordinary in-place (`---`) and named `--output=PATH` symlink, so no direct-write bypass persists. Add a mixed-writer regression: edit through link, run BIF, then inspect referent and link.
7. Assert atomic rename lands beside the referent in follow mode and no temp remains after successful validation. Observe inode changes and hardlink divergence to document limits, without asserting that mode/owner/xattrs are preserved by this feature.

## Non-goals and related work

- No automatic creation or pruning of symlink farms; no policy for symlinked directory components, directory targets, or tree traversal.
- No general atomic-write hardening, temp naming redesign, metadata cloning, hardlink preservation, or race-free symlink defense in this ticket. This policy chooses **which file** to replace, not how to preserve its inode.
- No owner/group or SELinux policy implementation: see `bif-ecy` and `bif-ccn`. Current `--attributes` supports chattr-style changes on the new file only.
- No `validate-only` symlink mode: `bif-symlinks` mentions it as experimental, but the three requested write policies plus existing `--read` give a smaller, testable contract.
